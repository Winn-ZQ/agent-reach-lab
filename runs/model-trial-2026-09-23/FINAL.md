# 首轮模型试测收尾：可连接，尚无可直接交付的终稿

日期：2026-09-23。真实 API 调用；Qwen3.8-Flash 与 DeepSeek-V4.1-Flash 均经百炼北京阿里直供。当前助手逐条对照输入材料审阅，未采用独立人工研究员盲评。每题单次运行，不能据此给出综合准确率或稳定性排名。

## 结论与采用建议

两款模型都能完成基本分析、保留部分未知并发现报告错误，也都出现了不能直接交付的问题。产品必须把接口成功、结构校验通过、证据支持、复核通过分开记录。当前没有可标记为已复核终稿的报告。

后续开发可优先验证 **Qwen 分析＋DeepSeek 独立复核**：Qwen 的 App 草稿较简洁，DeepSeek 在本次人工错误题的问题清单中覆盖较多。此组合尚未实际交叉测试，只是开发候选，不是正式选型或质量保证。两种角色均应可替换；先修复下面的输入和验证规则，再开展有限修正试测。

## 同题结果

### App 研究主场景

输入为同一份虚构 App A 官方说明与模拟笔记。6条候选中4条纳入、来自3名作者；X1与X2是同一作者，X5重复排除，X6日期未知而不纳入时间窗口。模型调用真实，但资料不是实际小红书采集。

两款分析均覆盖4个问题，自报 answered 3、unknown 1、omitted 0。未知项是全部用户的实际发生率；未知合理，但问题覆盖不等于答案正确。

- Qwen：功能、相反体验和下一步验证较清楚；未明确汇总4条笔记／3名作者、X1/X2同作者。Q3用省略号拼接引文，被程序发现。其复核首次输出不是合法JSON，无法交给调度器使用。
- DeepSeek：保留了同作者、排除记录和版本未知等限制，但出现“X1/X2两位用户（且同作者）”的矛盾表述；排除记录X5被生成空引用，任务级声明被错误归到S1。其复核提出了一些真实问题，也把X3同时归入“入口顺利”和“修改顺利”判作重复计数；多主题标签本来允许重叠，草稿没有把这些数相加当作独立用户，这属于误报。
- 本次未修改草稿再复核，因此不能说复核已经减少最终错误，也没有证明降低人工核验时间。

同一App题的分析＋初次复核：Qwen共8,447 Token／64.920秒，DeepSeek共8,131 Token／50.659秒。Qwen的原复核格式失败；修复另增加3,228 Token／26.816秒。两种模型的复核输入包含各自不同的草稿，只有分析输入完全相同。单次耗时受生成长度及服务状态影响，不能推广为一般速度优势；Token数也不等于人民币费用。

### 官网题

Qwen保留了全品牌型号兼容性未知，但引文拼接、日期判断和无证据品牌限定仍有问题。复核误用“当前2024/2025”判断2026年是未来。原文正文确实有2026年9月16日日期标签，结构化发布日期为空；不能把日期标签误说成模型完全凭空捏造。详见[首次停止时的逐项记录](RESULT.md)。DeepSeek没有有效官网答案，因此该题不能比较优劣。

## 最后一次格式修复的边界

使用Qwen原App复核请求的完全相同messages，只增加 `response_format: {"type":"json_object"}`，作为独立修复请求记录。原始失败未覆盖，修复不混入基线结果。

结果：返回合法JSON，但把任务字段 `disclosure`、`sampling` 写进只允许真实来源ID的 `source_ids`；本地返回 `check_schema`。同时模型给出pass，并未发现草稿的拼接引文和作者限制遗漏。应用必须拒绝这个通过状态。

JSON模式约束语法，不保证字段契约、引用和语义正确。下一版可验证更严格的JSON Schema，并继续本地验证。官方参数说明：[百炼结构化输出](https://help.aliyun.com/zh/model-studio/qwen-structured-output)。本次没有验证DeepSeek的JSON模式或任何模型的严格Schema模式。

## 输入侧也需要修复

原演示材料的声明包含“未调用模型API”，原意是说静态样例的制作过程。试测直接沿用后，两款模型都把它复制进真实API结果。这是我们的输入范围不清，不能全记为模型幻觉。下一版应拆为：

1. 数据属性：虚构功能与笔记，未真实采集小红书。
2. 运行属性：是否调用模型、调用时间、用量，均由程序台账填写，不让模型根据资料猜测。
3. 来源记录：正文引用和任务／采样元数据分开；不能把采样声明假挂在官网S1下。

v1输入及哈希保持不变，未来使用新版本目录，不能修改旧题使模型成绩看起来更好。

## 下一步实施顺序

1. 先离线完善输入契约：显式运行日期、连续原文引用、正文和采样元数据分离、作者去重和多主题计数规则；事实研究不强制制造改进假设。
2. 程序生成纳入笔记数、独立作者数、排除原因等可确定字段；在语义复核前阻止坏引用、无效JSON和不存在的来源ID。
3. 实现一次修正上限：草稿→程序检查→独立复核→必要时修正→再检查／复核；保留每版内容，预留复核调用，不足就交付明确标注的未通过草稿。无效复核不能把任务标成完成通过。
4. 下轮真实调用前另立预算；本轮已到12次上限。先用保存结果及模拟响应验证控制逻辑，再把流程接入本机研究网页。
